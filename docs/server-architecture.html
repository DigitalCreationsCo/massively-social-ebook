Important runtime distinction. Broadcast-configured channels run through BroadcastCoordinator + RealtimeEngine. The older channel-tick lifecycle remains reachable from development debug tooling and the batch/reader path; it is not the server-started live loop.

Runtime flows

What happens, in order

Request → reader

  1. Browser enters Node HTTP and receives timestamp, body parsing, CORS, logging, and session middleware.
  2. Route handler validates against shared Zod contracts and calls DatabaseStorage.
  3. Storage uses Drizzle + PostgreSQL; current channel state may be served from the process cache.
  4. Browser opens /ws?channelId=… for sync, votes, and chat. HLS is a separate playback session.

Schedule → episode

  1. Scheduler seeds scheduled sessions and checks due work every 30 seconds.
  2. At preroll, the broadcast coordinator asks the story pipeline for an ordered canonical window.
  3. Each slot prepares text, image, and optional narration; assets are archived and persisted.
  4. QueueBroadcast stages slots, then releases them serially at scheduled start. HLS delivers the live manifest.

Story → media

  1. RAG retrieves lore + relevant blocks; PX enriches the context and image references.
  2. NarrativeEngine / AI SDK returns structured story blocks under the configured provider.
  3. Image generation and TTS run concurrently where possible, with retry and fallback rules.
  4. GCS stores durable media; TTS and static delivery retain a local-file fallback.

Chat → fanout

  1. YouTube/Twitch connectors normalize incoming provider events.
  2. ChatGateway deduplicates, persists, and maps provider identities to channel users.
  3. FanoutHub broadcasts normalized messages to connected WebSocket clients.
  4. Reader-submitted chat follows the same gateway boundary before broadcast.

TTS → audio

  1. TTS route applies origin/API-key checks and a per-IP sliding-window limiter.
  2. Hugging Face Gradio generation is polled and WAV-validated.
  3. Audio is segmented, uploaded to GCS when configured, or written under public/audio.
  4. Proxy streams the archive and falls back to the local path if GCS is unavailable.

Shutdown → drain

  1. SIGTERM/SIGINT flips the shutdown guard to prevent duplicate cleanup.
  2. Scheduler stops; live broadcast runtime and game-loop cleanup drain.
  3. HTTP server closes; PostgreSQL pool ends last.
  4. Failures are logged and set a non-zero process exit code.
